# Invictus Warehouse — ecommerce platform

A custom storefront for Invictus Warehouse (South Africa): sneakers, clothing, new and pre-owned iPhones and the Invictus Collection. It owns the catalogue, cart, checkout, accounts, orders, inventory and admin, with no Take App dependency.

## Features
Storefront: editorial homepage, shop with URL-driven filters/sort/search (`/shop?size=9&brand=Nike`), category pages, product pages (variants, sizes, stock states, reviews, JSON-LD), instant search suggestions, wishlist, cart drawer + cart page (localStorage for guests, DB for signed-in users), guest + account checkout, order confirmation and tracking, WhatsApp buttons, About/Contact/legal pages, branded 404/error states.
Admin (`/admin`): dashboard (revenue, orders, products, low stock, customers, sales chart, best sellers), product CRUD with image upload and variants, inventory, orders + status updates, review moderation, coupons, business settings, configurable size sets.

## Tech stack
Next.js (App Router) · TypeScript · React · Tailwind CSS v4 · Framer Motion · Lucide · Supabase (Postgres, Auth, Storage) · Zod. Note: this Next.js version differs from older releases; see `AGENTS.md` and `node_modules/next/dist/docs/`.

## Architecture
- `app/` routes, API routes and server actions · `components/` UI by domain · `hooks/` cart/wishlist state
- `lib/data/` server data access (catalogue falls back to bundled seed data in **demo mode** when Supabase is not configured)
- `lib/payments/` `PaymentProvider` interface → Paystack (implemented), PayFast (stub)
- `lib/delivery/` `DeliveryService` providers: store collection, manual courier, local delivery; Uber Direct stub
- `supabase/schema.sql` schema + RLS · `supabase/seed.sql` catalogue seed (generated by `npm run seed:sql`)
- Security: prices/totals recomputed server-side from the DB; payment verified server-side (webhook + callback); stock decremented atomically via `decrement_stock()`; RLS on every table; admin checked on every action (`requireAdmin`) and by RLS (`is_admin()`); rate limiting on public endpoints; service-role key and secrets server-only.

## Local development
```bash
npm install
cp .env.example .env.local   # fill in values; without Supabase the site runs in demo mode (browse only)
npm run dev
npm run typecheck && npm run build
```

## Supabase setup
1. Create a project. 2. Run `supabase/schema.sql`, then `supabase/seed.sql` in the SQL editor. 3. Add URL, anon key and service-role key to `.env.local`. 4. In Auth → URL configuration add your site URL and `/auth/callback`. 5. Confirm the public `product-images` storage bucket exists.

## Admin setup
Register a normal account on the site, then in the SQL editor:
```sql
insert into admin_users (user_id) select id from auth.users where email = 'owner@example.com';
```
Then open `/admin`. Customers can never reach admin features (server checks + RLS).

## Payment setup (Paystack)
Set `PAYSTACK_SECRET_KEY` and `NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY` and point the Paystack webhook to `/api/payments/webhook`. Start with test keys. No card data is stored. **PayFast is a documented stub and not functional yet.**

## Product images
Matching seed-product images are served from `public/images/iphones` and `public/images/clothing`; products without a matching image show a branded placeholder. Seed SQL links those images to products, and the storefront also uses the matching image for existing seeded products without a database image. Manage product images in Admin → Products; mark borrowed images as "Reference" so they are labelled.

## Deployment (Vercel)
Import the repo, add the environment variables from `.env.example`, set `NEXT_PUBLIC_SITE_URL` to the live domain, deploy.
